A plan to extract structured features from narrative patient records and daily care chats with LLMs, validate them, and analyze them deterministically or with a second LLM pass. One extraction layer feeds teaching, reasoning review, and research.

Disclaimer. This is a research and medical education plan. It is not medical advice and not a clinical decision support tool, and nothing here should guide the care of a real patient. Architecture

Every downstream result can be traced to an extracted feature, and every feature to a sentence in the source text.

1. ExtractLLM runs prompts from the Clinical Cognition library against each narrative or chat thread. Output is strict JSON.
2. NormalizePydantic schema checks, ontology code lookup (SNOMED, LOINC, ICD-10, RxNorm), range checks.
3. VerifySecond model or second pass. Disagreements go to a human adjudication queue.
4a. DeterministicScores, guideline rules, cohort statistics, graph traversal. Same input, same output.
4b. LLM analysisDifferential critique, Socratic debrief, counterfactuals, bias flags.
LLM stepDeterministic stepHuman or consensus step

Outputs from 4a and 4b merge into a case report, a cohort dashboard, and exportable datasets for R, SPSS, or Stata.

Data sources

Two sources feed the extraction layer: case narratives and daily care chats. Case logs give the clinical picture at admission. Chats give the day-by-day course, the team's reasoning, and life at home.

Source 1, case narratives: avi33tbtt.github.io/cases/case_links.html

An index of nearly a thousand numbered links to public medical e-log blog posts: long cases, short cases, admissions, and case discussions, mostly general medicine (heart failure, CKD and AKI, fever and dengue, paraparesis, seizures, liver disease, and others).

Source 2, daily care chats

Daily conversations between the patient, the caretaker and the doctor team about managing the case and lifestyle and sharing updates. Not yet reviewed for format, language or volume.

Cautions before using either source
  • Privacy and consent (chats): chats carry phone numbers, names, group names, photos, and voice notes. Confirm consent and a data-use basis for every patient and caretaker, and de-identify before any LLM call.
  • Privacy (cases): public posts are not automatically safe to send to an LLM provider. Check for identifiers and consent text.
  • Linking: chats must be tied to the right case, and each message to the right speaker role. Errors here spread into every later result.
  • Informal language: chats are short, abbreviated, and may mix languages and transliteration. Extraction quality needs its own validation on chat text.
  • Advice is not a decision record: a doctor's message in a chat may be advice, a question, or a thought. Classify message type before treating anything as an order.
  • Not a gold standard: case logs are student-written and chats are informal. Clinician-labelled gold data is still required.
  • Selection bias: cases come from a few teaching-hospital units over roughly 2020–2023, and patients with active chat groups may differ from those without. Treat results as pilot findings.
  • Duplicates and format variation: remove repeated URLs and repeated cases before splitting development and held-out sets, or leakage will inflate scores.
  • Terms of use: confirm permission to reuse the source blogs, and record the source URL or thread ID with each record.

Phases

Each phase ends with a gate. Do not start the next phase until the gate is met.

Weeks 1–2Foundations and scope▸

Work

  • Choose one pilot use case: a retrospective case series, a rare-disease set, or a teaching case bank.
  • Collect 100–300 narrative records from the data sources, with the daily chat threads for the same patients where they exist. De-identify them and record the ethics or data-use basis, including consent for chat participants.
  • Select 5–8 prompts from the prompt library as the first extraction suite.
  • Run the completeness and de-identification audits (see the catalogue) on a 20-case sample and a matching sample of chat threads, then confirm the data-fit ratings before choosing the pilot question.
  • Define the variables the pilot question needs, and nothing more. Start from the variable dictionary.
  • Set up the repo, config, and a prompt versioning convention.
Gate: written pilot question, variable list, and approved de-identified dataset.
Weeks 3–5Extraction layer▸

Work

  • Design the feature schema (see Schema section) with certainty, negation, and source-span fields on every item.
  • Write and version extraction prompts, one per extraction unit (see the prompt families in the variable dictionary): case baseline, episode timeline, labs and vitals, medication, and certainty and negation.
  • Add chat prompts: link each message to its case and sender role, classify message type, then extract symptoms, medication taken, lifestyle, and red flags with timestamps.
  • Build the Pydantic validators and the ontology mapper with fallback to free text plus "unmapped" flag.
  • Add provider abstraction through OpenRouter so models can be swapped.
  • Cache every raw LLM response with prompt version, model, and parameters.
Gate: at least 95% of records produce schema-valid output on a first pass.
Weeks 5–7Validation harness▸

Work

  • Have a clinician label a 50–100 case gold subset for the key variables, including a sample of chat threads.
  • Compute precision, recall, and F1 per variable, plus agreement with confidence intervals.
  • Add dual-model or dual-pass consensus on high-stakes variables.
  • Build the adjudication queue: case text on the left, extracted features with highlighted source spans on the right.
  • Iterate prompts on a development split; freeze them and report on a held-out split.
Gate: each variable meets its pre-set F1 target on held-out cases, or is dropped or routed to human review.
Weeks 7–10Deterministic analytics▸

Work

  • Implement scores: Wells, CURB-65, qSOFA, and any scores specific to the pilot condition.
  • Encode guideline pathways as testable rules with unit tests.
  • Build cohort tools: phenotype definitions, case-control matching, propensity scores, clustering, survival models.
  • Build the hub-node graph model and trajectory traversal.
  • Run a sensitivity analysis: how do results change if extracted features are perturbed at the measured error rate?
Gate: every function has tests, and every output links back to feature IDs.
Weeks 9–12LLM-based analytics▸

Work

  • Differential extraction with supporting and refuting evidence.
  • Cognitive bias detection (anchoring, premature closure) over case reasoning text.
  • Counterfactual runs: remove or alter one feature and measure differential shift.
  • Socratic debrief generation against expert reference reasoning.
  • Feature-level uncertainty scoring from textual ambiguity.
Gate: expert review of a sample rates outputs as useful and not misleading; failure modes documented.
Weeks 12–15Interface, scale, and reporting▸

Work

  • Dashboard: cohort distributions, per-case drill-down, source-span viewer, export buttons.
  • Batch runner with resume, cost tracking, and rate-limit handling.
  • Reproducibility bundle: prompts, model IDs, seeds, schema, and data dictionary.
  • Pilot report and manuscript or internal write-up with validation results.
  • Decide what to scale: trial screening, pharmacovigilance, or education modules.
Gate: an independent person can rerun the pipeline from the bundle and reproduce the results.

Rules for every prompt
  • Extract facts only. Never ask the LLM for averages, totals, scores, or stages.
  • The model copies values and units as written. Code converts units and rejects values outside plausible ranges.
  • Allow "not stated". A missing value is not a normal value.
  • Keep each dose, reading, or message as its own event.
  • Version every prompt and rerun the gold set after any change.
Gate before writing prompts: check the dictionary against 20 cases and a matching sample of chat threads. Mark each variable as present, absent, or ambiguous. Drop or demote any variable below a coverage threshold that is set before the check.

Extraction prompts

Version 0.1 drafts for the diabetes and kidney disease pilot. Each prompt is derived from the variable dictionary. These are starting points to test on the audit sample, not final text.

Design choices
  • Exact quotes, offsets by code. Models count characters poorly, so every item returns the exact quoted words. Code finds the offsets and rejects any quote that is not in the source text.
  • No conversion or arithmetic by the model. Prompts copy values and units as written. Code converts units, sums insulin doses, and calculates eGFR and stages.
  • Roles and timestamps come from the chat export. The model never guesses who wrote a message.
  • The text is data. Blog posts and chats can contain instructions. The shared preamble tells the model to ignore them.

Analysis approaches


Every extracted feature feeds one of two downstream analytical engines: deterministic (rule-based, reproducible, zero hallucination) or LLM‑based (nuance, interpretation, critique). The choice depends on the task’s need for rigor versus reasoning.




Deterministic analyticsScores (Wells, CURB‑65, qSOFA), guideline compliance rules, cohort statistics (propensity scoring, matching), graph traversal for hub‑node detection, survival analysis, clustering, adherence/trajectory metrics. Same input always yields same output.


LLM‑based analyticsDifferential diagnosis ranking with supporting/refuting evidence, cognitive‑bias pattern detection, counterfactual “what‑if” perturbation, Socratic debrief generation against expert reasoning, uncertainty scoring from textual ambiguity. Handles gray zones and generates teaching material.

A1Normalize values and verify evidence spans▸
Method: Deterministic. Needs: P1 to P5 output; dictionary rows 15 to 26.
How to analyze
  • Run after every extraction call, before anything is stored as a feature.
  • Parse the first number in value_text, convert units with a fixed table, flag unknown units instead of guessing.
  • Find each evidence quote in the source text. No match means the item is unsupported and is dropped and counted.
  • Keep the original text next to the converted value so every number can be audited.
Python
import re

UNIT = {  # (test, unit) -> function to canonical unit
    ("creatinine", "umol/l"): lambda x: x / 88.4,
    ("creatinine", "mg/dl"):  lambda x: x,
    ("glucose", "mmol/l"):    lambda x: x * 18.016,
    ("glucose", "mg/dl"):     lambda x: x,
    ("hba1c", "mmol/mol"):    lambda x: 0.09148 * x + 2.152,
    ("hba1c", "%"):           lambda x: x,
    ("potassium", "mmol/l"):  lambda x: x,
}
LIMITS = {"creatinine": (0.1, 25), "glucose": (20, 1000),
          "hba1c": (3, 20), "potassium": (1.5, 9)}

def canonical(test, value_text, unit_text):
    m = re.search(r"\d+(?:[.,]\d+)?", value_text or "")
    if not m:
        return None, "no_number"
    x = float(m.group().replace(",", "."))
    u = (unit_text or "").lower().replace("\u00b5", "u").replace("\u03bc", "u")
    u = u.replace("micromol", "umol").replace(" ", "")
    f = UNIT.get((test, u))
    if f is None:
        return None, "unit_unknown"
    y = f(x)
    lo, hi = LIMITS[test]
    return round(y, 2), "ok" if lo <= y <= hi else "out_of_range"

def find_span(quote, text):
    """(start, end) in the original text, ignoring whitespace differences, else None."""
    norm, idx = [], []
    for i, ch in enumerate(text):
        if ch.isspace():
            if norm and norm[-1] != " ":
                norm.append(" "); idx.append(i)
        else:
            norm.append(ch); idx.append(i)
    n, q = "".join(norm), " ".join(quote.split())
    j = n.find(q) if q else -1
    return None if j < 0 else (idx[j], idx[j + len(q) - 1] + 1)

A2eGFR, CKD stage and KDIGO AKI stage▸
Method: Deterministic. Needs: P1 age and sex; P3 creatinine and UACR; P2 dialysis.
How to analyze
  • Compute eGFR with CKD-EPI 2021 (creatinine, no race term). The model never calculates it.
  • Stage CKD (G and A categories) only from a stable value, such as pre-admission or at discharge. eGFR is not valid while creatinine is changing, so never stage chronic disease from an AKI peak.
  • Stage AKI from the creatinine series: rise of 0.3 mg/dL within 48 hours, or 1.5 times the lowest value in the prior 7 days. The 7-day minimum is a proxy when no true baseline is documented, so record which one was used.
  • Chronic labels also need a duration of more than 3 months. If duration is unknown, output the stage as provisional.
  • Where creatinine is missing the output is unknown, not stage 0.
Python
from datetime import timedelta

def egfr_ckdepi_2021(scr_mgdl, age, sex):
    k, a = (0.7, -0.241) if sex == "female" else (0.9, -0.302)
    e = 142 * min(scr_mgdl / k, 1) ** a * max(scr_mgdl / k, 1) ** -1.200 * 0.9938 ** age
    return round(e * (1.012 if sex == "female" else 1.0), 1)

def g_stage(egfr):
    for cut, g in [(90, "G1"), (60, "G2"), (45, "G3a"), (30, "G3b"), (15, "G4")]:
        if egfr >= cut:
            return g
    return "G5"

def a_stage(uacr_mg_g):
    return "A1" if uacr_mg_g < 30 else "A2" if uacr_mg_g <= 300 else "A3"

def kdigo_aki(series, rrt_started=False):
    """series: time-sorted [(datetime, creatinine_mgdl)]. Returns [(datetime, stage 0-3)]."""
    out = []
    for i, (t, v) in enumerate(series):
        prior7  = [x for s, x in series[:i] if t - s <= timedelta(days=7)]
        prior48 = [x for s, x in series[:i] if t - s <= timedelta(hours=48)]
        stage = 0
        if prior7:
            r = v / min(prior7)
            stage = 3 if r >= 3 else 2 if r >= 2 else 1 if r >= 1.5 else 0
        if prior48 and v - min(prior48) >= 0.3:
            stage = max(stage, 1)
        if v >= 4.0 and stage >= 1:
            stage = 3
        if rrt_started and stage:
            stage = 3
        out.append((t, stage))
    return out

A3Glycaemic trajectory and hypoglycaemia burden▸
Method: Deterministic. Needs: P3 and P5 glucose readings with context (dictionary row 22).
How to analyze
  • Work in readings, not time. Capillary checks are taken when symptoms or schedules prompt them, so call the result percent of readings, never time in range.
  • Report per case: mean, variability (CV), percent of readings below 70 and below 54 mg/dL, 70 to 180, above 250, and fasting mean.
  • Always print the number of readings and days with data beside each metric. Suppress metrics with fewer than about 10 readings.
  • Link each hypoglycaemic reading to the insulin dose and meal nearest before it using timestamps. List the pairs for clinician review rather than claiming cause.
Python
import pandas as pd

def glucose_metrics(df):
    """df columns: ts (datetime), mgdl (float), context (str). One row per reading."""
    d = df.sort_values("ts")
    g = d["mgdl"]
    per_day = d.set_index("ts")["mgdl"].resample("D").count()
    return {
        "n_readings": len(g),
        "days_with_data": int((per_day > 0).sum()),
        "mean": g.mean(),
        "cv_pct": 100 * g.std() / g.mean() if len(g) > 2 else None,
        "pct_below_70": 100 * (g < 70).mean(),
        "pct_below_54": 100 * (g < 54).mean(),
        "pct_70_180": 100 * g.between(70, 180).mean(),
        "pct_above_250": 100 * (g > 250).mean(),
        "fasting_mean": d.loc[d["context"] == "fasting", "mgdl"].mean(),
    }
Check: Compare with a manual tally on a sample of days. Report missing days per case.
A4Insulin doses and adherence▸
Method: Deterministic. Needs: P4 doses_taken; P5 doses (dictionary rows 27, 28, 32).
How to analyze
  • Parse units from dose_text in code and sum per day. Never let the model add doses.
  • Score reported doses: yes = 1, partial = 0.5, no = 0. Drop unclear and count it.
  • Adherence here is among reported doses. Silence is not a missed dose, so always show reporting coverage (days with any report) next to the score.
Python
import re

def units(dose_text):
    m = re.search(r"(\d+(?:\.\d+)?)\s*(?:u\b|units?|iu)", (dose_text or "").lower())
    return float(m.group(1)) if m else None

def adherence(doses):
    """doses: DataFrame [date, drug, taken], deduplicated across P4 and P5."""
    w = {"yes": 1.0, "partial": 0.5, "no": 0.0}
    d = doses[doses["taken"].isin(w)].assign(score=lambda x: x["taken"].map(w))
    per_day = d.groupby(["date", "drug"])["score"].mean().rename("adherence").reset_index()
    coverage = doses.groupby("date").size().rename("reports")
    return per_day, coverage
Check: Match to a manual regimen timeline on a sample. Report unclear-dose share.
A5Red-flag rules and escalation lead time▸
Method: Deterministic and LLM. Needs: P5 red_flags and readings; clinician-labelled escalation events.
How to analyze
  • Two layers: rules on numeric readings (code) and the red-flag phrases from P5. The union is the alert list.
  • Test against clinician-labelled escalations (call, visit, admission). Without that label file, report counts only and no accuracy.
  • Report sensitivity within a window (start at 48 hours), false alarms per patient-week, and median lead time from first flag to escalation.
  • Thresholds are starting values for a clinician to confirm.
Python
from datetime import timedelta

RULES = {  # name: (reading kind, predicate)
    "severe_hypoglycaemia": ("glucose", lambda v: v < 54),
    "marked_hyperglycaemia": ("glucose", lambda v: v > 400),
    "hypotension": ("sbp", lambda v: v < 90),
    "severe_hypertension": ("sbp", lambda v: v >= 180),
    "hypoxia": ("spo2", lambda v: v < 92),
    "oliguria": ("urine_ml_24h", lambda v: v < 400),
    "hyperkalaemia": ("potassium", lambda v: v >= 6.0),
}

def rule_flags(readings):
    """readings: iterable of (ts, kind, value, feature_id). Returns [(ts, rule, feature_id)]."""
    return [(ts, name, fid) for ts, kind, v, fid in readings
            for name, (k, pred) in RULES.items() if k == kind and pred(v)]

def evaluate(flag_times, escalation_times, window_h=48):
    w, hits, leads = timedelta(hours=window_h), 0, []
    for e in escalation_times:
        prior = [f for f in flag_times if timedelta(0) <= e - f <= w]
        if prior:
            hits += 1
            leads.append((e - min(prior)).total_seconds() / 3600)
    false = sum(1 for f in flag_times
                if not any(timedelta(0) <= e - f <= w for e in escalation_times))
    leads.sort()
    return {"sensitivity": hits / len(escalation_times) if escalation_times else None,
            "false_alarms": false,
            "median_lead_h": leads[len(leads) // 2] if leads else None}
Check: Review every false alarm with a clinician to tune thresholds on the development split only.

A8Counterfactual runs and robustness to extraction error▸
Method: Deterministic and LLM. Needs: Verified feature table; error rates per variable from the gold set.
How to analyze
  • Counterfactual: code removes one feature (or flips its certainty), runs A-P9 on the edited list, and measures how the differential moved. The LLM never edits the case.
  • Run the baseline several times first. If the baseline differential changes between repeats, shifts smaller than that noise mean nothing.
  • Robustness: for the final analysis, flip binary variables at the measured false-negative and false-positive rates and repeat. Report the interval for each key statistic.
Python
import numpy as np

def dx_shift(base, cf, k=3):
    """base, cf: ranked diagnosis labels already mapped to codes."""
    return {"top1_changed": base[0] != cf[0],
            "topk_overlap": len(set(base[:k]) & set(cf[:k])) / k,
            "rank_of_base_top1": cf.index(base[0]) + 1 if base[0] in cf else None}

def perturb(df, rates, seed):
    """df: 0/1 columns. rates: column -> (false_negative_rate, false_positive_rate) from the gold set."""
    rng, p = np.random.default_rng(seed), df.copy()
    for col, (fn, fp) in rates.items():
        r = rng.random(len(p))
        p[col] = np.where(p[col] == 1, (r >= fn).astype(int), (r < fp).astype(int))
    return p

def stability(df, rates, stat, n=500):
    """stat: function(df) -> number. Returns baseline and the 2.5, 50, 97.5 percentiles."""
    sims = [stat(perturb(df, rates, s)) for s in range(n)]
    return stat(df), np.percentile(sims, [2.5, 50, 97.5])
