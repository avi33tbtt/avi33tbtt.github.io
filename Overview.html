Site 1 · Hub

The idea

Just as vibe coding lets developers build software through natural language, Vibe Rounds applies the same paradigm to clinical reasoning. It is defined as a Socratic AI paradigm for students, clinicians, researchers and scientists that augments reasoning through structured questioning, guided discovery and reflective dialogue rather than direct answers.

“AI that questions, not answers.”

The clinician stays the decision-maker. The AI plays the attending: it challenges assumptions, surfaces relevant biases, offers a second opinion and flags what was oversimplified. It is a learning tool, not a diagnostic one.

Bring your own key. The learner tools run in the browser; the API key lives in local storage and goes straight to your chosen provider. Not for real patient care.

The pedagogical spectrum

Five stages move from instructor-centred to learner-centred. Vibe Rounds claims stages 3–5.

1 Lecture

Foundation: shared vocabulary and framing.

2 Dyadic

Peers explain to each other, forcing encoding.

3 Socratic ★

Stress-test understanding with “Why?” and “What if?”. Home base of Vibe Rounds.

4 Guided discovery ★

Scaffolded problems; tiered hints build the environment on demand.

5 Research ★

N-of-1 protocols, case analytics, evidence mapping.

The progression is justified by Cognitive Load Theory: starting at research overwhelms novices, and staying at lecture never builds independent thought.

Ten constraints that keep the AI Socratic

Appended to any #VibeRounds persona (Supportive Intern, Junior Resident, Socratic Attending), they stop a helpful model from simply filling the silence when a learner types “idk”.

1 Forced commitment before any hint.

2 Minimum effort: “idk” gets a redirect, not help.

3 Delayed rescue (the 10-second rule).

4 Tiered hints: framework → direction → partial → summary.

5 Effort-weighted depth of help.

6 Grade reasoning, not only correctness.

7 Adaptive difficulty.

8 Role-calibrated rigor.

9 Reflect before reveal: “What could kill the patient?”

10 Answer-withholding until attempt, revision or explicit surrender.

Example: given a 54F with dyspnea and pleuritic pain after a 14-hour flight, the AI won’t accept “PE” at face value. It asks why PE ranked first, what you’d expect if it’s wrong, and what chest X-ray finding would make you regret anticoagulating (aortic dissection).

The hub also documents a prompt evolution from simple persona (L1) to OSCE-style examination mode (L6), and a “What / Where / Do” template for capturing initial reasoning.

Site 2 · Prompts library

The Learning Stack

Not a flat prompt list but layers: frameworks shape how a prompt teaches, modules define what and when, and a lifecycle gives every session the same shape: Initiation → Execution → Closure.

Four frameworks (woven into modules)

FrameworkRole
A · Humanistic PersonaBuilds confidence alongside competence; specific affirmation before challenge.
B · Fink’s taxonomy (FLINK)Six non-hierarchical dimensions, from foundational knowledge to learning-how-to-learn.
C · Bloom’s revisedRemember → Create, mapped to clinical tasks; calibrates difficulty.
D · Critical AwarenessNames the biases of the framework itself (automation, anchoring, hallucination).

Module coverage

Coverage is organised by a learner’s moments, not by organ system: M01 Socratic reasoning; M04 ward practice (rounds, admissions, pre-op, polypharmacy, triage); M09 seven-stage N-of-1 research protocol; M10 journal reading; M25 Bloom-stratified question bank; M42 Clinical Pre-Mortem. Start at Module 0 (cold-start orientation). The library’s own review calls maturity uneven: some parts are mature, others explicitly experimental.

Guided Discovery: “an MRI for clinical thinking”

Instead of asking “what is the diagnosis?”, it asks how thinking moves from uncertainty to understanding. Three building blocks: modules (single lenses), agents (orchestrated multi-framework runs) and pipelines (e.g. 1 → 12 → 9 → 21 → 35).

Observation→Pattern recognition→Hypotheses→Decision architecture→Bias detection→Metacognition

CCOS: six cognitive layers

  1. Clinical reasoning (illness scripts, differentials, Bayesian)
  2. Workflow engine (sequencing, pipelines)
  3. Metacognitive monitoring (bias, assumptions, uncertainty)
  4. Epistemic trust: calibrated numbers, risk-based claim verification, decision spectrum (conservative → maximal), multi-domain confidence
  5. Decision architecture
  6. Learning and documentation
CCOS is a structured prompt architecture, not software with persistent state. The trust layer is prompt-level uncertainty framing, not automated verification.

Site 3 · Research

Clinical Intelligence Suite

A tool for building a cohort and running deterministic, auditable analytics. Its stated purpose is prototyping: surface patterns worth pursuing, then take them to a proper platform (OHDSI ATLAS, TriNetX) and a designed study. It is not clinical decision support.

Workflow: ask → define → appraise → explore → test → review → record

Discover (backward lift)→Interpret (LLM, optional)→Test (forward / closed loop)→Decide (human gate)

The LLM only drafts text and proposes a test query. Every number comes from deterministic code, and a person approves or rejects before anything counts as a finding candidate. In the worked example, an older Neuro/MSK hypothesis gave escalation 92.3% vs 86.7% (lift 1.07, n=65): small, unadjusted, and best rejected or retested.

Analytics grouped by question

Cohort overview, data quality, patient segments; backward lift, co-occurrence, phenotype clusters, knowledge graph; forward hypothesis, PICO/PECO, Cox, closed loop (re-tests findings with lift ≥1.35 on a fresh cohort).

Disease modules

Hypertension, Type 2 diabetes and COPD each have 15 passes and 4 decision analytics (e.g. resistant hypertension flag, white-coat pattern, intensification candidates).

Architecture and tech

Monorepo: React/Vite web app, Fastify API, and three analytics registries (V1 113, V2 119, V3 49) over one shared core (@viberounds/core). Data sources are FHIR R4, CSV/NDJSON import, a synthetic generator or PostgreSQL (100k–1M+ patients via SQL aggregation). The LLM layer supports OpenRouter, Claude, OpenAI and Gemini, receives summaries only, and every run and decision goes to an audit log.

Intended “code goes to the data” design: multicentre queries run inside each site’s reviewed analytics library, with small-count suppression and query logging, so only aggregates leave. This is a design, not a shipped feature, as is the open community-analytics idea (Experimental → Tested → Validated maturity levels).

Status: done: 100+ analytics, disease modules, journey map, DB mode, generate-and-test loop. Deferred: auth and multi-tenancy, scheduling, CI/deployment, SQL versions of non-hypertension modules.

Good practice and caveats

  • Treat every output as a draft to verify; the default cohort is synthetic, so results show workflow, not clinical truth.
  • Comparisons are unadjusted, many analytics run at once (chance findings), and V3 outcomes are modelled at import, so stratifying them is circular.
  • Learning tools are not diagnostic. The hub and CIS both state that all output needs independent clinical verification.
  • A browser AI assistant sees on-screen data and sits outside the app’s guardrails; check policy before using one with real data.
