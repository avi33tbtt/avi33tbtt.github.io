Vibe Rounds: AI that questions, not answers

A paradigm for using AI to deepen clinical reasoning, built as two connected lanes: person-centred tools that train how one case is thought through, and one population-centred app that speeds up how many cases are explored at once.

  • Author Dr. Avinash Kumar Gupta

  • Status education and research use, not clinical decision support

What it is. AI tools and prompts that make clinical learners do the reasoning (the AI asks, the human commits), in two lanes: person-centred tools for one case and a population-centred analytics app.

What exists. Browser-based Socratic tools, 57+ CCOS prompt modules, an evidence-mapping workflow (worked ASV example), a FHIR analytics app and three courses.

Status. For education and research, not clinical decision support. The benefits are design hypotheses; no learner outcome study has been reported yet.

The project in one picture

Everything except the Clinical Analytics app is person-centred: one learner, one case, one chain of reasoning at a time. The Analytics app is population-centred: cohorts, prevalence, trends and care gaps across many patients. Both end at the same place: a human decides.

Figure 1. Synthesis of the hub documentation and the analytics app’s About page.

Why it matters for learning gains. The same design bet runs through both lanes: learners and analysts do the thinking, the AI shapes and challenges it. This is a design hypothesis grounded in cognitive load theory, the generation effect and desirable difficulties. The project’s own documentation states that no learner outcome study has been reported yet.

The five stages of learning

Vibe Rounds sits on a spectrum that moves from instructor-centred to learner-centred. It claims stages 3 to 5 (marked ★) and maps each to a part of the project.

StageCentred onWhat happensIn Vibe Rounds
1. LectureInstructorShared vocabulary and framingFoundation; not claimed
2. DyadicPeerPeers explain to each other, which forces encodingNot claimed
3. Socratic ★SelfStress-test understanding with “Why?” and “What if?”Hub and learner tools (person-centred)
4. Guided discovery ★Self, scaffoldedScaffolded problems; tiered hints build the environment on demandPrompt library and CCOS (person-centred)
5. Research ★Self or researcherCase analytics, evidence mappingEvidence maps and the Clinical Analytics app (population-centred)

The progression is a design hypothesis informed by cognitive load theory and the expertise-reversal effect: starting at research overwhelms novices, and staying at lecture never builds independent thought.

Stage 3: Socratic learning

Lane 1: person-centred clinical cognition

Scope: learn and explore how a single case is reasoned through. All tools run in the browser with the learner’s own API key (Claude, Gemini, ChatGPT or an OpenAI-compatible endpoint) and are intended for fictional, synthetic or de-identified cases only.

Socratic toolset (Stage 3)

  • Practice: Case Bench, Case Simulator, Clinical Practice, Case Question Bank, Lesson Bench, Dx Dojo
  • Debate: Clinical Polemos, a stakeholder-persona panel
  • Lenses: Case Lens (8 lenses), SDM Lens (7 domains, patient’s voice), EBM Query Generator
  • Navigation: Complex Flow Builder
  • Prompt kits: Case Analytics and Case Reading for Google NotebookLM
How to use: bring your own key (BYOK)
  1. Open a tool, for example Case Bench. No account or install is needed; it runs in your browser.
  2. In Step 1: Model, choose Claude, Gemini, ChatGPT or Other (any OpenAI-compatible endpoint). Paste your own API key and the model name. The tool has a “Where do I get a key?” link, and usage is billed by your own provider.
  3. Your key is stored only in this browser’s local storage and is sent directly from your browser to the provider you chose.
  4. In Step 2: Case, paste a fictional, synthetic or de-identified case (vignette, discharge summary, your own notes, or a case link), or generate a sample case at a chosen difficulty.
  5. Pick a mode (for example Dialogue or Analytics in Case Bench) and commit to your own answer before asking for hints.

Ten constraints stop the model from “filling the silence”: forced commitment, minimum effort, delayed rescue, tiered hints, effort-weighted help, grading reasoning, adaptive difficulty, role-calibrated rigor, reflect-before-reveal, answer withholding.

Stage 4: Guided discovery

Guided discovery: CCOS (Stage 4)

  • 57+ prompt modules, 4 frameworks (Humanistic Persona, Fink, Bloom, Critical Awareness), lifecycle Initiation → Execution → Closure
  • Six cognitive layers: reasoning, workflow, metacognition, uncertainty framing, decision architecture, learning
  • Shadow Modules: adversarial, self-auditing counterparts
  • Orchestration: Module 59 (adaptive pipeline orchestrator)
  • Two run modes: Socratic (AI asks, learner commits) and analytics (learner supplies a case, AI works through the module and returns a text, Markdown or HTML report)
How to use: case text or link, plus the Complex Flow Builder
  1. Get your case ready as de-identified text, or as a link to it.
  2. Open the Complex Flow Builder. Use + Add case link for the case, then drag modules onto the canvas and connect them in the order you want. A node can branch into several paths.
  3. End every path with End: Create .md File or End: Create .html File to choose the output format.
  4. Click Copy .txt (or Export .txt). This gives a ready prompt with your case, the ranked paths, a link to each module, and the output instructions.
  5. Paste it into an LLM chat that can open links, so it can read each module and run the paths in rank order. If your LLM cannot open links, paste the module text from the prompt library yourself.
  6. To use just one module, open its file in the prompt library and paste it into the chat with your case. Read and critique the result; do not accept it as written.

CCOS is a structured prompt architecture, not software with persistent state. Its uncertainty layer is prompt-level framing, not automated verification.

How CCOS is built, shown through Module 52 (Clinical Pearls)

CCOS modules are plain-text prompt files that a learner pastes into any AI chat. Module 52 (“Clinical Pearls Distillation”, status mature in its own header) turns research evidence into bedside-ready pearls. It shows every building block in one place: a lifecycle, layered steps, patient anchors, AI modes and all four frameworks.

Its design problem: a pearl fails through false precision, not brevity. The module therefore deconstructs the evidence first, then compresses it, so each pearl states its own scope.

1. Lifecycle: Initiation, Execution, Closure

Initiation (CP.0 to CP.1)Load the evidence and extract the core finding; anchor it to a real de-identified patient.
Execution (CP.2 to CP.11)Five layers of distillation, from what the finding claims to how it fits local resources.
Closure (CP.12 to CP.15)Critical awareness debrief, exportable pearl set, significant-learning check, difficulty for the next session.

2. The execution layers

LayerStepsWhat the learner doesAI mode
1. Evidence boundaryCP.2, CP.3Map population, setting, comparator and outcome; test the boundary against a second patientTraditional; Devil’s Advocate
2. Effect calibrationCP.4, CP.5Translate effect size into absolute terms, CI and NNT; then attack what the numbers cannot warrantTraditional; Devil’s Advocate
3. CompressionCP.6, CP.7Draft three candidate pearls; stress-test the best against a third patient for safety and scopeTraditional; Devil’s Advocate
4. Teaching and retentionCP.8, CP.9Bloom-level teaching pearl and vignette; three memory architectures tried on a fourth patientTraditional; Brainstorming
5. IntegrationCP.10, CP.11Check against the current guideline landscape; translate to a resource-constrained context using a fifth patientTraditional; Devil’s Advocate

Five steps are patient-anchored. The learner pastes a brief de-identified vignette and the AI tests whether the pearl applies, partly applies, or must be withheld for that patient, which guards against applying a population statement to someone outside the source population.

3. Where the four frameworks sit in Module 52

C. Bloom’s revised taxonomyCP.8, teaching pearlLevels Remember, Understand, Apply, Analyse, Evaluate, Create set the difficulty. The module notes Analyse is most valuable: it trains recognition of the boundary case where the pearl fails

4. Beyond one module

  • Modules are single lenses organised by learner moment. Pipelines chain them, for example 1 → 12 → 9 → 21 → 35, composed in the Complex Flow Builder; Module 59 orchestrates adaptively.
  • Shadow modules are adversarial, self-auditing counterparts.
  • Every module is tagged A to E for what its output may honestly claim, from genuine analysis to dependence on real input supplied step by step.
  • Module 52 offers entry paths by purpose (for example a teaching session: run the full module, then export CP.13 and the CP.8 vignette).

5. Two ways to run the same module

Each CCOS module can be run in either of two modes. The module file and its lifecycle stay the same; what changes is who does the work in each step.

Socratic modeAnalytics mode
How it startsThe learner works through the module step by stepThe learner gives a case once (or the evidence, for Module 52) and hands the module prompts to the AI
AI’s roleAsks, challenges, withholds answers until the learner commits; tiered hints under the ten constraintsWorks through the module’s steps itself, as a structured analysis of the supplied case
Learner’s roleCommits to an answer before any help; reasoning is gradedReads, checks and critiques the finished analysis
OutputA live transcript, a reasoning trail and a debriefA finished text, Markdown or HTML report; Complex Flow Builder pipelines end in a node that writes a .md or .html file
Best forBuilding reasoning skill, practising before you know the answerFast structured review of a case, second opinions on your own reasoning, teaching material, consistent write-ups across many cases
Main riskSlower; depends on the learner engagingA complete-looking answer can replace the learner’s own thinking, and the AI may fabricate specifics it was not given

Module 52 shows the analytics side clearly. Its own file says it contains no Socratic prompts by design, because it distils evidence into the clinician rather than testing prior knowledge. In analytics mode the learner supplies the paper or guideline summary, and the AI runs CP.0 to CP.15 in order and returns the final pearl set (CP.13), the Bloom teaching pearl and vignette (CP.8), the critical awareness debrief (CP.12) and the next-session difficulty (CP.15). Its five patient-anchored steps need real de-identified vignettes; without them they are best left out or clearly marked as placeholders. For a Socratic route into the same clinical topic, the module points to Module 1 on a related case, run before Module CP.

The Case Bench tool offers the same split: a Dialogue mode (Socratic rounds, case audit, differential challenge, quick quiz) and an Analytics mode that produces a one-pass report through a chosen lens.

Why this design. Bloom sets how hard the question is. Fink widens the learning beyond cognition to values and learning strategy. The persona keeps challenge from turning defensive, and Framework D keeps the learner from over-trusting the AI. The same lifecycle opens and closes every session, which makes sessions comparable and auditable.

In plain terms: how this architecture helps

For the learner

  • In Socratic mode you do the thinking. The AI asks and challenges, so reasoning is practised rather than outsourced.
  • In analytics mode you get a fast structured review. The AI works the case through the module and you critique the result.
  • Shows your blind spots. Bias audits, devil’s-advocate steps and pre-mortems expose anchoring and premature closure.
  • Right-sized difficulty. Bloom levels and the difficulty ratchet raise the challenge as you improve.
  • Whole-person learning. Fink’s dimensions and the humanistic persona add values, the patient’s view and learning strategy to the facts.

For teachers, reviewers and safety

  • Repeatable. The same open, work, close shape makes sessions comparable and easy to review.
  • Honest about limits. Patient-anchored steps and A to E tags stop a pearl or module claiming more than it can support.
  • Low barrier. Plain text in any AI chat: nothing to install, easy to fork, adapt or critique.
  • Composable. Single lenses chain into pipelines for different cases and learners.
Evidence status. These are design intentions grounded in learning science. The project’s documentation reports no learner outcome study yet, so the benefits above are not yet measured. The learning evaluation in the plan below is the step that would test them.

Stage 5: Research

Research is generating or testing something that could hold beyond the one patient in front of you. Every output traces back to a source and a human verifies it.

Worked evidence

ArtefactWhat it shows
ASV evidence mapEvidence-pyramid trajectory mapping for anti-snake-venom. Mortality signal sits in case reports; RCTs and meta-analyses are not designed to show it. Built with the Evidence-Pyramid Trajectory Mapper prompt (details below).

How to use: build an evidence map from your own papers
  1. Choose the research papers you want to map. They should address the same question and outcome, ideally from more than one study design.
  2. Open the Evidence-Pyramid Trajectory Mapper prompt on GitHub and paste it into an AI chat.
  3. Give it one paper at a time (as text or a file). It names the study design, applies the matching module and returns an interactive HTML map for that paper. Save each map.
  4. Once you have papers from several designs, ask it to run the evidence-pyramid climb (Module G). It places each paper in its tier and marks how adjacent tiers reinforce, attenuate or contradict each other.
  5. Check each extraction against the original paper. The map is a reading aid, and a human verifies it.

Prompt behind the ASV map: Evidence-Pyramid Trajectory Mapper

One system prompt, Prompts/evidence-pyramid-trajectory-mapper.md, that is pasted into an AI chat with one paper at a time. It is a router plus module set: it first identifies the study design, applies the matching module, and returns an interactive HTML map. It does not run searches itself; the PubMed search and paper selection happen before it.

PartWhat it does
Step 0: classify designNames one primary design (case report or series, case-control, cohort, cross-sectional, RCT, systematic review or meta-analysis) and the evidence for it before anything else. Mixed papers get one dominant module; unclear ones are stated and the better-supported design is used.
Modules A to FOne module per design, each with the same skeleton: extract, merge into a network, build the HTML plot. Only the unit of analysis changes: a patient (A), a subject traced backward (B), a forward trajectory (C), a snapshot cell (D), a trial arm (E) or an included study (F).
Module G: evidence-pyramid climbRuns after each paper has its own A to F output. Checks that the papers share a comparable question and outcome (G0), distils one 3 to 5 node signal chain per paper (G1), then places each paper as a node in its design’s tier, from case reports at the base to meta-analyses at the apex (G2). Edges between adjacent tiers are marked reinforcing, attenuating, contradicting or unresolved, and the clearest chain of papers is traced as the climb path.
HTML outputA single self-contained file with a tiered diagram, hover tooltips per paper, and a prominent toggle to show only reinforcing edges (solid evidence) or only contradicting and attenuating edges (shaky evidence).

Why it suits the ASV question. Each tier keeps its own native units: a case-series impression is never converted into a number, and an RCT interval is never turned into an anecdote. That is how the map can show a signal in case reports without pooling incompatible evidence.

Built-in safeguards:

  • Uses only data present in the paper; missing values are marked, not estimated.
  • Never pools or averages effects across papers, unless a paper is itself a meta-analysis that reports the pooled estimate.
  • Declines to draw a pyramid when only one design tier is present, and splits or excludes papers with different outcomes or populations.
  • Carries each paper’s own citation into the chat summary, the HTML tooltips and a final reference list; no anonymous “Study 7” labels and no invented citations.
  • Applies Vibe Rounds branding, a disclaimer banner and collapsed module sections to every output.

The repository documents the ASV workflow (one paper at a time into a running map, tiers kept separate) and does not name the prompt file explicitly. This prompt is the one that matches that description.

Lane 2: Clinical Analytics app (population-centred)

Try it: Vibe Rounds Clinical Analytics app (About page).

One line: ask better questions of clinical data, and know how far to trust the answers. It is deliberately lightweight: it reads FHIR as it is (no common data model conversion) and is meant for the exploratory step before platforms such as OHDSI ATLAS or TriNetX.

  1. Bring data. Own FHIR files (JSON, NDJSON, CSV), the open HAPI test server, or a deterministic synthetic generator. Imported into PostgreSQL batches.
  2. Check the data first. Coding coverage, unrecognised code systems and date problems are measured; “analytics readiness” runs every analytic once per method and reports which the data can support.
  3. Define the cohort. Plain-English question fills a PICO or PECO form; a SNOMED CT query builder writes cohort SQL with descendant or ancestor expansion (from RF2 or CSV hierarchies).
  4. Run the analytics in five readings. V1 notes, V2 codes, V3 codes plus approved enrichment, V4 codes with dates, V5 enriched codes with dates. Seeing up to five answers side by side shows how much a result depends on method.
  5. AI assistant or AI researcher. The model reads results, flags findings, proposes up to four next analytics. The researcher chains 1 to 20 rounds; the analyst can stop, continue or review each query.
  6. Look at the data and approve enrichment. Patient explorer, cohort knowledge graph (lift, order, typical gap in days), care pathways and trajectories. For text-only records the model proposes real candidate codes and a person approves, edits or rejects each.

Who it serves

  • Clinical researchers and quality analysts for fast first answers and reusable SQL
  • Informatics students and educators, as a teaching sandbox for cohort logic
  • FHIR engineers and developers needing realistic test data

Not for clinical decisions, real patient data without approval, multi-site or publication-grade studies, or very large datasets.
