CCIS
System Architecture

A repository-grounded account of the Contextual Clinical Intelligence Standard and its standalone application: declarative clinical-knowledge packages, strict validation, compatibility resolution, deterministic execution, reproducible run records, the local package market, and the future cohort-intelligence layer.

Architecture reference25 November 2026Implementation-awareStandalone HTML

Vibe Rounds CCIS is a separate, local-first clinical intelligence application and a versioned standard for the artefacts it consumes. It imports a bounded context export from the EMR Enhancer, checks whether versioned knowledge packages can be used with that context and runtime, executes declarative analytics through a constrained deterministic engine, and produces traceable results. Its longer-term direction adds reusable decision graphs, research-to-package authoring, cohort analytics and a Cohort Context Graph. Those later capabilities must not be confused with the current 0.1.0 runtime.

Architecture thesis. The EMR owns the patient record. CCIS owns the standard, the package execution environment and the analytical run record. Knowledge is expressed as independently versioned artefacts, validated before use, pinned by checksum and interpreted by a deterministic whitelist engine. Patient context crosses the boundary as an export file; CCIS does not connect to or mutate the EMR database.

1. Overall system architecture

CCIS is intentionally not a conventional server-side analytics service in its first release. The 0.1.0 architecture is local-first: a static browser application and a Node.js command-line interface use the same JavaScript domain modules. There is no CCIS application server or database in this release. Imported patient context and generated run records are handled locally by the user.

Interpretation: the browser and CLI are two interfaces over shared domain logic, not separate analytics implementations. 2. CCIS standard and artefact model

CCIS is more than one JSON format. It is a versioned specification suite for declarative clinical-knowledge artefacts and the contract between those artefacts, an importing application and a deterministic engine. Artefact versions, standard versions, engine versions, operator-set versions and FHIR versions are independent dimensions.

Versioning and lifecycle

  • Stable identifiers do not depend on display labels.
  • Published content is immutable; changes create a new version.
  • References identify exact versions or declared version ranges, never silently resolve to “latest”.
  • Superseded versions remain addressable for reproducibility.
  • Lifecycle states include Draft, Submitted, In Review, Reviewed, Validated, Conditionally Validated, Deprecated, Withdrawn and Rejected.
  • Structural, semantic, clinical, execution and security/privacy assurance are recorded separately. Software validation does not establish clinical validation.
Design consequence. A package is not merely a query or a rule snippet. It is a scoped, versioned, testable and governable unit of clinical knowledge that declares what it needs, what it computes, what it means and what it must not be used to conclude.

3. Validation, compilation and package lifecycle

Artefacts pass through a fail-closed validation pipeline before they can be compiled, published to the local market or selected for execution. The compiler creates canonical bytes and a SHA-256 checksum. A checksum establishes byte identity; it does not establish publisher identity, clinical correctness or safety.

Validation records explicitly leave clinical, execution and security/privacy assurance as not assessed where no such evidence exists.

4. Import, compatibility and execution runtime

The runtime sequence starts with a context envelope exported by the EMR. The importer creates a canonical context and import report. The compatibility resolver evaluates the selected pathway and its analytics against the held package versions, the imported context and the runtime. Only eligible packages proceed to planning and execution.

Compatibility is an explicit decision, not fuzzy matching

Each compatibility entry reports six checks: artefact, semantic, schema, data readiness, runtime and assurance suitability. Matching uses exact identifiers, versions or declared ranges, field keys and units. Similar names or near versions do not count as matches.

OutcomeMeaningExecution implication
CompatibleAll required checks are met.May run under the applicable execution policy.
Compatible with limitationsModel is usable with explicit constraints.May run with limitations shown.
Needs dataPackage matches, but required context data is missing.Normally skipped; explicit opt-in can run packages designed to report missingness.
IncompatibleOne or more required checks fail or cannot be evaluated.Refused.
Not eligibleStatus, scope or intended use does not permit use.Refused.

Deterministic execution model

  • The executor is a whitelist expression interpreter. Package content is declarative; it cannot supply executable JavaScript.
  • The 18 implemented operators include boolean logic, comparisons, arithmetic, time difference, declared conversion, conditional evaluation, count and selection.
  • The engine uses three-valued logic. Unknown inputs remain unknown and do not silently become false, zero or normal.
  • Execution has step, depth and output-size limits. A refusal produces no partial value.
  • Pathway decision nodes inspect recorded states and produce a trace of states, considered outcomes and the route taken. An indeterminate node stops at its report stage rather than guessing.
  • Pure modules have no network, filesystem, clock, randomness, eval or Function access.
Important scope distinction. The current snake demonstration proves the runtime mechanics for a bounded process-measurement use case. It is not a general autonomous clinical decision engine and does not issue treatment recommendations.

5. Clinical semantics, uncertainty and provenance

CCIS treats the meaning and status of a clinical record as first-class information. An input is not just a scalar. Its concept, unit, source, effective time, recorded time, collection time, state and relationship to the applied element all matter to whether an analytic may use it.

Source classes include patient-reported, clinician-entered, clinician-verified, imported, device, derived and AI-proposed. A derived value records its inputs and derivation. AI-proposed content cannot silently become clinician-verified. Numeric comparisons require matching units or a declared, versioned conversion; the engine does not guess a conversion.

Why this matters. “No measurement”, “measurement unknown”, “not collected”, “not applicable” and “negative” are different clinical situations. Keeping them distinct prevents analytics from turning missingness into false reassurance and makes the limitations of every result inspectable.

6. Run records and reproducibility

A CCIS run is an immutable, content-addressed account of what was requested and what happened. The record identifies the pathway and analytics versions, checksums, standard and engine versions, operator set, input snapshot, supplied parameters, evaluation time, route and results. Re-running from the record is designed to reproduce the same bytes when all inputs and versions are unchanged.

Record properties

  • One run record represents one request and its input identity.
  • Package and pathway versions are pinned; no implicit “latest” substitution.
  • The input snapshot is retained in the record so a rerun does not depend on a mutable external source.
  • Evaluation time is an explicit input, not read from the system clock inside the pure engine.
  • Records can be verified, rerun and compared. Changed inputs or versions produce a distinct identity.
  • Failed execution records contain no partial results; refusal messages do not echo sensitive input content.
  • Exported run records can be retained by the user as files; 0.1.0 does not provide a shared server-side history.

The repository acceptance path checks the end-to-end slice against hand-calculated fixtures. The README documents byte-identical reruns and refusal to overwrite a different existing record.

7. Package market and browser application

The local market is a controlled catalogue of immutable artefact releases. It resolves exact versions, verifies checksums, supports pins and refuses unsafe publication conditions. Its patient-data lint is a screening mechanism, not proof that an artefact is safe or free of patient information. The future remote marketplace is a separate distribution step.

8. Cohort intelligence and the Cohort Context Graph

Cohort-level intelligence is a major part of the intended CCIS direction, but it is not the same as the current single-context runtime. The build plan deliberately sequences cohort definitions, three-valued eligibility, cohort analytics, aggregation, privacy controls and the Context Graph after the initial standalone slice and authoring/distribution work.

Planned graph model

The planned Cohort Context Graph is an aggregate, derived in-memory projection—not a patient-level identity graph and not a causal model. Its planned node families include cohort, condition, observation concept, pathway, analytic output and time window. Declared and co-occurrence edges describe relationships visible in the data; they must not be presented as proof of causation. A relationship-map interface and time-window navigation are planned, with small-cell masking carried through from the cohort analytics phase.

Why the graph is valuable

Once implemented, the graph can make it easier to explore how cohort definitions, conditions, recorded concepts, pathways, analytic outputs and time windows relate. It can expose patterns, missingness and pathway variation while keeping the provenance and population scope visible. These are analytical relationships, not causal conclusions or automatic clinical recommendations.

9. EMR integration and FHIR Mode

The EMR–CCIS boundary is file-based and contract-driven. The EMR Enhancer creates a versioned context envelope; CCIS validates and imports it. CCIS does not query the EMR database, write back to clinical observations or assume the EMR's internal tables. The import report makes accepted, rejected, unmapped and ambiguous records visible.

sequenceDiagram
 participant EMR as EMR Enhancer

 CCIS->>CCIS: Build canonical context + import report
 CCIS-->>APP: Accepted context
 APP->>APP: Compatibility, pathway and analytics execution
 APP->>OUT: Export immutable run record
 OUT-->>EMR: Optional user-mediated hand-off / review

Envelope boundary

  • The contract carries a pseudonymous case reference, exact applied element/pathway versions, observations and events, values and units, effective/recorded times, states, source classes, provenance, terminology verification state and export metadata.
  • Identity and narrative are excluded by default. Entered-in-error records are excluded by default.
  • Import is all-or-nothing at the envelope level for contract failures. Individual records are classified as accepted, rejected, unmapped or ambiguous.
  • No values, timestamps, zones or units are silently invented. Unit conversion occurs only through a package-declared conversion in the runtime.

FHIR Mode

The repository contains a FHIR-mode example with a Questionnaire representation, a CCIS contextual element and a mapping report. This demonstrates an intended conversion boundary and visible mapping limitations. It does not establish a complete FHIR server, comprehensive resource support, full profile conformance or lossless round-trip interoperability. Phase 6.1 remains the planned capability-matrix and conformance-testing work.

Complementary roles. FHIR is a standards-based representation and exchange mode. The CCIS context envelope is the project's bounded runtime-import contract. They serve related but different purposes and should not be conflated.

10. Security, privacy and governance

Security is enforced through constrained execution, explicit data boundaries, validation, safe UI construction and traceable package governance. The local-first architecture reduces the need to centralise patient context in the first release, but it does not by itself establish production security or privacy compliance.

AI boundary

AI is deliberately absent from CCIS 0.1.0. The build plan places governed LLM drafting in Phase 4.3: off by default, explicit switch, whitelist payload, source references, draft-only output, and no authority to publish or validate. Clinical thresholds, doses, bands and formulas must not be supplied by a language model; threshold parameters are owned by a named local clinician and default to disabled.

Clinical safety statement. The repository labels the project as a prototype using synthetic data only and not for clinical use. Its artefacts have not had clinical review; demo numbers are not clinical values. Software tests, schema conformance, reproducibility and a “validated” package status must never be represented as proof of clinical safety or effectiveness.

12. Architectural contribution and design interpretation

CCIS's distinctive contribution is the combination of a formal clinical-knowledge contract with a reproducible, constrained execution environment. It creates a bridge between reusable clinical knowledge and patient-context analytics without making the intelligence platform the source of truth for patient records.

1. A standard for clinical knowledgeReusable elements, groups, pathways, decision nodes, analytics, terminology and validation artefacts are versioned independently.
2. Explicit semantic compatibilityPackages declare their requirements; CCIS explains whether the context, versions and runtime match.
3. Deterministic analyticsClinical calculations are executed by a constrained engine, not generated by an LLM.
4. Uncertainty-preserving reasoningMissing, unknown, conflicting and not-applicable states remain distinct through the pipeline.
5. Reproducible analytical evidenceChecksums, pinned versions, input snapshots, traces and immutable run records explain what ran.
6. A path to population intelligenceCohort analytics and the Cohort Context Graph extend the same semantic discipline to aggregate relationships, provenance and time.

Concise thesis. Vibe Rounds CCIS is a standalone, standards-oriented clinical intelligence environment that imports bounded clinical context, validates and resolves versioned knowledge packages, executes deterministic analytics and pathway logic, and records reproducible results—with a planned extension into governed cohort intelligence and a Cohort Context Graph.
