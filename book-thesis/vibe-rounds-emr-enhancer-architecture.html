EMR Enhancer
System Architecture

A repository-grounded account of the clinical data model, reusable clinical knowledge, pathway composition, contextual documentation, standards-based interoperability and the EMR–CCIS exchange boundary.

Architecture reference25 November 2026Implementation-awareStandalone HTML

The Vibe Rounds EMR Enhancer is best understood as a clinical information platform with a governed knowledge layer and a controlled intelligence-exchange boundary. It is not simply a collection of dynamic forms. Its central architectural move is to keep patient-specific clinical records separate from reusable, versioned clinical definitions, then connect them through explicit case applications and traceable data exchange.

Architecture thesis. Patient records describe what happened to a particular patient. Element sets and pathways describe reusable clinical knowledge. Case-level pins record exactly which version of that knowledge was applied. The contextual export boundary packages a controlled view of the case for CCIS without giving the analytics engine unrestricted write access to the source clinical record.

2. Database architecture and entity relationships

The central modelling distinction is between reusable definitions and patient-specific use of those definitions. A published element-set version is a reusable knowledge artefact. A case-applied set is a patient-case-specific pin to that exact version. Observations are recorded against the applied set and field definition, preserving the context in which the value was captured.

Observation semantics

The observation route validates submitted values against the exact pinned element-set version. The implementation accepts supported field types such as text, number, integer, boolean, select and datetime, and handles explicitly unknown values. It does not silently coerce a value into another type or convert an incompatible unit. Derived fields are not stored as ordinary observations.

Observation provenance includes the applied-set relationship, field key, value type, effective time, recorded time, source type, status and recording actor. Corrections are represented as new records linked to the prior record; erroneous entries are marked rather than physically erased.

Why the separation matters. A value such as a blood pressure reading is not just a number. It has a patient case, a clinical field definition, a version of the definition, a unit, an effective time, a recording time, a source and an author. The data model makes those relationships explicit.

3. Reusable clinical knowledge: authoring, review, versioning and pathways

Element sets are reusable definitions. They can express structured fields, types, options, units, rationale and coding bindings. Their lifecycle is governed: draft definitions are linted, submitted for review, approved and published as versions. Pathways compose these published versions into ordered workflows.

Versioning and reproducibility

  • Stable identity: an element set remains the same conceptual artefact as it evolves through versions.
  • Immutable published versions: publication creates a governed version rather than silently changing a version already in use.
  • Review before publication: the review workflow separates authorship from approval and includes role-based reviewer rules.
  • Exact pathway references: pathway steps refer to specific element-set versions, not merely the latest version of a set.
  • Case pins: applying a set or pathway creates case-specific references to the selected versions.
  • Explicit upgrade: a newer version is applied as a deliberate update; the previous application is superseded rather than rewritten.
  • Withdrawal without erasure: a set can stop accepting new values while its prior application and observations remain traceable.

Illustrative example

A hypertension pathway could contain an initial assessment set v2, a blood-pressure monitoring set v3 and a follow-up care set v1. Applying the pathway to a case pins those versions. If the monitoring set later advances to v4, the existing case does not silently inherit v4. A clinician or authorized workflow must explicitly update the application.

Terminology note. Disease, care and template are useful conceptual categories for explaining the library. The precise supported kinds and validation rules should be taken from the current element-set schema and seed definitions rather than assumed from this explanatory diagram.

4. Clinical documentation lifecycle

5. Contextual elements and multi-context cases

A clinical context is a useful conceptual lens for selecting relevant knowledge and interpreting observations. It is not necessarily identical to a diagnosis code. A patient may have multiple simultaneous clinical concerns, and a case can bring together the relevant documentation and monitoring structures.

For a patient with diabetes, CKD and hypertension, a case may need diabetes-specific documentation, renal monitoring and blood-pressure monitoring. Implementation boundary. The repository supports explicit element-set and pathway applications to cases. The richer idea of a general-purpose context ontology, automatic context inference, cross-context dependency resolution and unified multi-context analytics should be treated as an evolving design direction unless a corresponding implementation is verified in the code.

Terminology bindings

The element-set model can associate fields with code-system bindings. The code registry and verified-only export approach are intended to prevent unverified codes from being represented as verified clinical coding. The task tracker records nine code systems and notes that live terminology-server verification had not been tried at the time of that tracker entry.

Do not overstate standards conformance. The repository contains FHIR SDC-oriented functionality and mapping work, but a comprehensive, production-conformant FHIR server or complete import/export implementation across Patient, Encounter, Condition, Observation, Questionnaire and QuestionnaireResponse should not be claimed without resource-level conformance tests and interoperability evidence.

7. EMR → Context Envelope → CCIS → Run Record

This is a key architectural boundary. The EMR creates a context envelope from a consistent database snapshot. The export is audited and hashed. CCIS consumes that envelope and creates a run record. The EMR imports the run record only after validating its schema, case reference and connection to an envelope that the EMR actually exported for that case.

Context envelope safeguards visible in the implementation

  • The case-context endpoint is permission-protected and does not accept query parameters.
  • It reads one case snapshot in a repeatable-read, read-only transaction.
  • It reads applied sets, applied pathways, observations and a count of clinical events.
  • The event rows are counted but not exported by the inspected context route.
  • Entered-in-error observations are excluded by the envelope-building contract.
  • Patient identity and narrative are intentionally withheld from this export route.
  • The export is limited to 50,000 observations.
  • A configured context reference secret is required.
  • The exact JSON body is SHA-256 hashed; the export row and audit entry are written before the file is sent.
  • The audit record stores counts, hashes and withheld metadata, not clinical values.

CCIS run import safeguards

  • The imported record is validated against JSON schemas for the run-record contract and its component structures.
  • The record must carry the envelope SHA-256 extension.
  • The case reference must match the case reference generated for the target case.
  • The EMR verifies that the envelope hash belongs to an export previously created for that same case.
  • The run record is stored with its own canonical-JSON SHA-256 hash.
  • Duplicate imports are handled idempotently using the case and run-record hash.
  • The import path stores the run record; it does not write back to observations, notes, element sets or other clinical tables.
  • Acknowledgements are separate records, attributed to the signed-in user.
Architectural significance. CCIS is not granted direct authority to mutate the EMR's source clinical record. The exchange is snapshot-oriented and the return path is record-oriented. This supports analytical separation, provenance and controlled human review.
Known integration gap. The inspected CCIS importer documents a hand-off extension for the envelope hash because the CCIS run record did not yet carry that hash natively. The integration therefore depends on this explicit extension being preserved across the hand-off.

AI boundary

The task tracker describes AI execution on the server rather than exposing a provider key in the browser, with a mock provider used for the recorded implementation stage. The broader architecture should keep AI proposals distinct from clinician-authored and verified clinical records. AI-derived or proposed content should be explicitly labelled, reviewed where appropriate and prevented from silently becoming authoritative patient data.

10. Architectural contribution and design interpretation

The system's most distinctive contribution is not any one screen or export format. It is the way the components are connected:

1. Canonical clinical recordPatient, encounter, case, observation, event and note structures provide a persistent clinical information foundation.
2. Governed reusable knowledgeElement sets are versioned and reviewed independently of individual patient records.
3. Composable clinical pathwaysPathways assemble exact versions of reusable definitions into a reproducible sequence.
4. Context-aware applicationCase pins connect the patient-specific record to the precise reusable knowledge applied.
5. Controlled intelligence exchangeA versioned context envelope enables a separate analytical engine to work on a bounded snapshot and return a verifiable run record.

Why this differs from a conventional form-centric EMR

In a form-centric system, the form often acts as the main organizing object. Here, the form-like element set is a reusable, governed definition; the patient-specific application is separately recorded; and the resulting observations remain linked to the version used. This gives the system a route toward reproducibility, longitudinal interpretation and analytical reuse.

Relationship to the wider Vibe Rounds ecosystem

The EMR Enhancer is the clinical information and contextual capture side. CCIS is the separate clinical analytics and reasoning side. Vibe Rounds' broader Socratic learning and clinician-cognition direction can consume or work alongside these capabilities, but should not be conflated with the EMR's source-of-truth responsibilities or represented as an autonomous clinical decision-maker.

Concise thesis. Vibe Rounds EMR Enhancer is a case-centred clinical information architecture that separates patient-specific records from governed, reusable clinical knowledge; connects them through version-pinned pathways and contextual documentation; and exposes a controlled, auditable exchange boundary to a separate clinical intelligence platform.
