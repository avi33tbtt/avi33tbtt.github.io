Sharing a proof-of-concept: VibeRounds Clinical Intelligence Suite

This is Phase 05 of a five-phase architecture I've been working through in a project report ("From Person to Pipeline") — the phase where the pattern gets implemented as a real, browser-native FHIR analytics tool.

The core question I was trying to answer: how do you let an LLM participate in clinical cohort analysis without letting it become the source of truth for any clinical fact?

The architecture I landed on:

  • Every statistic — co-occurrence density, time-to-escalation, lift ratios, 40 passes total — is computed by deterministic code against real or synthetic FHIR data. The LLM never sees raw patient data and never generates a number.
  • The LLM's only job is interpretation and drafting: it can suggest a plain-language hypothesis about a pattern already computed, and it can draft one testable query — but that query only ever executes as ordinary filtered code, never as model output treated as fact.
  • Two human checkpoints sit between any AI-touched output and anything counting as a "finding" — one before a drafted query runs, one before its result is accepted.

It's a single-file, zero-backend app — queries CORS-enabled FHIR endpoints directly or runs on a client-side synthetic cohort, so there's nothing to stand up to try it.

Usability — how to actually use it:

  • Nothing to install: open the file (or the link) in a browser and it runs a synthetic cohort automatically. No account, backend, or FHIR server required to explore the full suite.
  • To try it against real data, switch the Data source panel to a SMART on FHIR sandbox or paste in your own CORS-enabled FHIR base URL (and a bearer token, if the server needs one) — every one of the 40 analytics re-runs against whatever cohort comes back.
  • Every section (chart, table, and narrative writeup) is independently collapsible, so a reviewer can jump straight to one analytic via the sidebar instead of scrolling the whole run — "Collapse all sections" gives a table-of-contents view of just the headers.
  • The Build Your Own and per-case Explorer panels let you query any field/outcome combination on demand — not limited to the 40 fixed passes — and drill into any single patient's full trajectory graph.
  • The (opt-in, BYOK) LLM layer only activates if you supply your own API key in the collapsed panel near the top; without one, the whole dashboard still runs end-to-end on deterministic code alone.

Benefits of this pattern:

  • Trustworthy by construction, not by review: because every number comes from deterministic code, there's no step where a reviewer has to catch a hallucinated statistic — the LLM structurally can't produce one.
  • Faster hypothesis testing: what would normally take custom database scripting per question collapses into seconds of human-validated query-and-run, without lowering the bar on what counts as a finding.
  • Auditable end to end: every case is traceable back to its own coded fields, so a reviewer or auditor can walk from any chart or table above back to the specific records behind it.
  • No infrastructure to stand up: a single static file that runs in any browser, against synthetic data, a public sandbox, or a live FHIR server — nothing to deploy just to evaluate the idea.
  • Generalizes beyond this dataset: the same deterministic-compute / LLM-interpret / human-gate shape extends to other cohorts, other coded fields, and other outcomes without redesigning the architecture.

To be clear about what this is and isn't: it's a pattern demonstration, not a validated tool. One synthetic/single-server cohort, no control arm, no clinical validation, illustrative (not production) SNOMED CT/ECL mappings throughout. The point isn't the 40 analytics themselves — it's testing whether "deterministic-compute, LLM-interpret, human-gate" holds up as a workable shape for AI-assisted population health tooling.

VIBEROUNDS · CLINICAL INTELLIGENCE SUITE — FHIR COHORT DASHBOARD

One cohort, mapped as trajectories, then fourty analytics — live in your browser

The VibeRounds Clinical Intelligence Suite demo is a zero-footprint, browser-native analytics platform designed to bridge HL7 FHIR datasets with deterministic population analytics and human-in-the-loop AI discovery. Built entirely as a single-file static application, it bypasses heavy backend dependencies by querying CORS-enabled FHIR endpoints directly or using client-side synthetic cohorts. The suite organizes patient journeys across a 6-checkpoint continuum (Observation → Diagnosis → Intervention → Outcome), applying 40 non-generative, hardcoded statistical passes—such as co-occurrence density, time-to-escalation, and 2×2 lift ratios—to isolate high-risk cohorts, health disparities, and care gaps with absolute mathematical precision.

While not intended as a real-time bedside decision tool or bi-directional EHR writer, the platform excels as an interactive, dual-engine discovery sandbox for population health managers, informaticists, and clinical researchers. Its "Build Your Own Data" (BYOD) engine enables multi-node querying across disparate clinical dimensions, dynamically rendering relationships into visual SVG networks and trajectory flowcharts. Rather than relying on ungrounded AI text generation, VibeRounds uses an opt-in LLM layer exclusively to translate pre-computed statistics into plain-language hypotheses and executable FHIR/ECL query logic. This structure accelerates hypothesis testing from weeks of custom database scripting down to seconds of human-validated analysis. Regenerate the cohort, or reconnect to a FHIR server, to re-run the whole dashboard, or jump straight to the full analytics catalog.

This dashboard is an MVP built on top of the "From Person to Pipeline" project report — the report's Phase 05 ("FHIR Cohort Pipeline — Full Analytics Run") in particular. Same design rule as the report: deterministic code computes every statistic, an LLM only interprets and (opt-in) drafts the next query, and a human checkpoint sits before anything counts as a finding. ▾Clinical analytics flow — one case through all 40 passes

A worked, illustrative example of how a single patient's trajectory gets touched by most of the analytics above, in the order a reviewer would actually use them: from raw signal, to pattern, to population context, to a bedside decision. Numbers are representative of the kind of output each pass produces on a cohort, whether synthetic or pulled live from FHIR — not a live read of the current regeneration — reload the case explorer above for the live per-patient graph. If a BYOK key is set, each of these passes can also generate an optional live LLM hypothesis on top of its already-computed numbers, and turn that hypothesis into one closed-loop coded test — drafted by the model, run as deterministic code, gated by two human checkpoints; that layer is walked through separately below, under Technical details.

Case 68-year-old with type 2 diabetes and hypertension, admitted for a fall, now three weeks into a new symptom the trajectory map first flagged as an unexplained checkpoint jump.
1

Trajectory map — where the case sits

Observation → Diagnosis → Intervention → Outcome shows the fall converging with a diabetes hub node instead of resolving cleanly, with hypertension modulating the plan (dosing caution on any new agent).

Signal: checkpoint jump from Observation straight to Intervention, skipping a clean Diagnosis node — a marker the map treats as worth a second look, not an error.

2

Diagnostic ambiguity + symptom proximity

Ambiguity scoring flags the post-fall symptom as sitting near two plausible diagnoses in embedding space; symptom-proximity clustering shows it co-occurring, in the wider cohort, with early neuropathy more often than with a simple soft-tissue injury.

Signal: ambiguity score in the upper band for this cohort, proximity weight tilted toward the neuropathy cluster.

3

Co-occurrence, polypharmacy & pharmacovigilance

Co-occurrence linking pulls in a recently added medication; polypharmacy scoring pushes the patient into a higher-interaction band; pharmacovigilance cross-checks that medication against the adverse-event pattern seen elsewhere in the cohort.

Signal: the new medication is a known contributor to the same symptom cluster from step 2 — a candidate drug-effect hiding behind what looked like a fall complication.

4

Risk scoring, time-to-escalation & LOS/disposition

Risk scoring places the patient in the upper-middle band once the drug-effect hypothesis is weighted in; time-to-escalation shows a shorter-than-median window for similar profiles; LOS/disposition modeling nudges the discharge plan toward a monitored step-down rather than straight home.

Signal: escalation risk high enough to justify holding the new medication and re-checking before discharge.

5

Population context — equity, SDOH, high-utilizers, readmission drivers

The equity check confirms this pattern doesn't skew toward a demographic-access issue; SDOH linkage flags transport as a barrier to the recommended follow-up; high-utilizer and readmission-driver models both mark this patient as a near-term readmission risk if the medication issue isn't resolved before discharge.

Signal: the readmission risk is driven by the access barrier, not by the drug-effect itself — two separate problems that need two separate fixes.

6

Guideline adherence, care gaps & symptom burden — closing the loop

Guideline adherence checking shows the neuropathy work-up wasn't ordered per protocol; care-gaps flags it as open; symptom-burden scoring shows the patient's overall load is high enough that closing this one gap materially changes the trajectory outcome, not just the single symptom.

Outcome: hold the suspect medication, order the guideline-indicated work-up, arrange transport support before discharge, re-score in 72 hours.

Clinical usefulness — comment

Chained end to end like this, the suite's real value isn't any single pass — it's that a possible drug-effect and a transport barrier, which usually surface on different rounds by different people, land in the same view before discharge. That's a genuinely useful catch pattern for a chart review or a teaching exercise on how these signals connect.

The honest limits: it runs on a synthetic, in-browser cohort with no real labs, imaging, or clinician notes behind it, so every "signal" here is a plausible pattern the model generated, not a verified finding. There's no validation against outcomes, no calibration against a real EHR, and the ambiguity/risk scores are illustrative rather than clinically calibrated. As a rounding-companion prototype or a way to teach analytic reasoning across a trajectory, it's strong; as anything used to change a real patient's care, it isn't — and the suite says so in its own footer.

ABOUT

▾About VibeRounds

VibeRounds is a client-side exploration of what a FHIR cohort looks like when it's walked through a person-centered trajectory — Observation → Diagnosis → Intervention/Plan → Outcome, with comorbidities modulating or constraining the plan — and then run through the full breadth of analytic types a clinical analytics catalog is usually asked to cover: discovery and replication, clinical/diagnostic, public-health/population, and patient/evidence-centered passes. Above the 40 fixed passes sits Build your own, the general engine those passes are all specific instances of — any node or AND-stacked combination of nodes, pointed at any outcome, run as a one-off query or handed to a planned/exploratory loop, with the query itself either hand-built, typed as plain language and matched by a deterministic lookup, or drafted by an LLM against the same fixed field catalog.

How it runs Entirely in your browser. A synthetic 500-patient cohort is generated on load, or you can point it at a public SMART on FHIR sandbox or your own FHIR server. No server-side processing, no data leaves the page unless you supply your own endpoint.
What it's for A teaching and prototyping surface for reasoning about cohorts across many analytic lenses at once — the kind of breadth a single retrospective chart review rarely has time for — plus, via Build your own, a way to ask the one question none of the 40 fixed passes happens to cover.
What it isn't Not clinical decision support, not validated against real outcomes, and not a substitute for clinician judgment. Synthetic-cohort results should be read as illustrative of a method, not as a finding about real patients.

Built as an MVP on the "From Person to Pipeline" project report

VibeRounds is the MVP implementation of the pattern described in avi33tbtt.github.io/project-report.html, a five-phase project report tracing this idea from a person-centered graph schema through a coded FHIR + SNOMED CT pipeline, a backward-reasoning ("outcome → candidate causes") engine, and a closed loop that drafts its own next query — with a human checkpoint before any finding counts as real. This app corresponds most directly to the report's Phase 05, "FHIR Cohort Pipeline — Full Analytics Run" (12 analytic passes on one synthetic cohort), extended here to the report's full 30+ analytic-type catalog and wired to optionally pull real cases from a FHIR server instead of only synthetic data. The same non-negotiable rule from the report holds throughout this app: generative AI is never allowed to invent a clinical fact — every rate, lift ratio, and hub node here is a direct read from computed data; an LLM (opt-in, BYOK) only interprets a finding or drafts the next question, and nothing re-enters the page as a confirmed pattern without a person clicking through the checkpoints below.

Node selection follows the Avinash Principle

The report's Phase 01 names the idea this whole app is built on: a full patient clinical journey, exploded into a decision tree, contains hundreds of millions of theoretical paths — but clinicians don't walk that tree. They make decisions by pruning noise and focusing on the tiny subset (under 1% of nodes) that actually carries "gravity" for the case in front of them. The Avinash Principle is built into VibeRounds' core design — it's just implemented two different ways depending on whether you're using the fixed analytics passes or Build your own, and it's worth naming both explicitly, because the second one is easy to miss.

1. Pre-selected pruning — the 40 fixed passes The concept: a full clinical decision tree runs to hundreds of millions of theoretical paths, but clinicians make decisions by pruning noise and focusing on the small subset of nodes known in advance to carry actual gravity.

How it's used: each of the 40 built-in passes is a pre-selected pruning decision — a specific comorbidity, category, medication, or symptom chosen in advance because it's known to carry gravity for that analytic lens. The app has already done the pruning for you before you open the section.
2. Reviewer-led pruning — Build your own Why it might feel like the principle isn't being used here: when you're exploring on your own, the app stops pre-selecting nodes for you and hands the pruning decision directly to you — so there's no visible "this is the gravity node" cue the way there is in a fixed pass.

How it works: instead of a hardcoded path, any field in the catalog (QB_FIELDS) can be queried against an outcome and kept or discarded based on its computed lift — letting you test both explainable nodes (pathophysiology — diagnoses, medications) and experiencable nodes (narrative/behavioral — housing, missed follow-ups) to see which ones actually carry leverage.

In short, the principle is active throughout the suite: the 40 fixed passes apply it automatically on your behalf, while the interactive tools let you apply it dynamically yourself. Either way, it trades a pure "data science" approach — casting a net over massive, unstructured data and hoping an algorithm finds hidden correlations in the noise — for something closer to how clinicians actually reason:

  • Domain knowledge first. The system assumes the clinician or domain expert already has real clinical intuition about which variables matter — the high-leverage "gravity" nodes — based on physiological plausibility and experience, rather than treating every field as equally worth searching.
  • Testing & outlier detection, not invention. The engine's job isn't to invent new clinical theories from scratch; it's to quantify the lift of a suspected pattern, validate known clinical paths, and surface genuine high-leverage outliers — while discarding what's just noise. It's targeted, high-yield validation designed around how clinicians actually think and practice, not blind pattern-matching over universal data.

Underneath both is the same bifurcation check the report calls out for every high-leverage node: the same lever that helps a cohort can also hurt it, so a node only earns its place by showing a real, computed outcome effect — never by being interesting a priori. Whether that check happens automatically (fixed passes) or on demand (Build your own), no node is ever kept on the strength of its story alone. QB_FIELDS itself is the same catalog mapped onto the FHIR resources above (Condition, Observation, MedicationRequest, Encounter, Patient), and the trajectory map builder below turns this into something you can actually assemble: pick nodes from that catalog yourself, watch each one's live gravity score, and chain the ones that clear the bar into a custom person-centered trajectory.

Where Build your own is actually useful — and where it isn't

Real gains Removes the "no fixed pass covers this" wall — any node or AND-combination, against any outcome, in seconds instead of a dead end. The natural-language box lowers the entry cost further: a reviewer who doesn't know QB_FIELDS or ECL syntax can type a sentence and get a working, auditable filter. And because it reuses the exact expr()/ECL/FHIR machinery the 40 fixed passes use, none of that speed comes at the cost of trust in the numbers — the LLM only ever picks a field/value from a fixed catalog; it never computes a rate or sees case data.
Real ceiling It's still one synthetic (or single-sandbox) cohort — no amount of query flexibility turns a screening signal into a finding. NL parsing is only as good as QB_FIELDS: anything genuinely outside the catalog (a lab trend, a free-text nuance) still can't be asked, on either path. The value here is concentrated in exploration and reviewer usability, not in generating new evidence — it's a faster way to ask a coded question and get a traceable, human-checked answer, not a way to skip the checkpoint or the validation study a real deployment would still need.
TECHNICAL DETAILS

▾Technical details, for builders

Everything an engineer needs to understand, extend, or re-platform this dashboard: architecture, data model, the analytics pipeline, FHIR integration, rendering approach, and known limitations. This whole app is a single static HTML file — there is no build step and no backend.

Stack & runtime

Zero-dependency, single file One .html file (~5,100 lines): inline <style>, inline <script>, no bundler, no npm packages, no framework. Fonts (Fraunces / Inter / IBM Plex Mono) load from Google Fonts over <link>; everything else is vanilla ES2017+ JavaScript executed directly by the browser.
Rendering model No virtual DOM. Every section is built by string-templating HTML (helper el(tag, cls, html)) or hand-drawn SVG, then injected via innerHTML/appendChild into a single root #app container. State lives in plain JS variables (CASES, INDEX_CASE, rngState, etc.), not a store — components that need to react to state changes (like the index-case comparison) expose a manual re-render function rather than subscribing to anything.
Deploy target Anything that can serve a static file: file://, S3/CloudFront, GitHub Pages, a CDN. No server-side code runs; the only network calls are optional, user-initiated, in-browser fetch() calls to a FHIR server the person chooses.

Synthetic cohort generator

Deterministic when seeded. seedRng(s) sets rngState; rand() is a mulberry32 PRNG, layered with randInt(), choice(), poisson(lambda), and randClamp(mean, spread) for bounded jitter. buildCohort(seed) loops genCase(id, cat, dataset) to synthesize ~500 patients across a fixed set of diagnostic categories, each with:

  • Demographics (age, sex, derived from FHIR-style fhirAge(birthDate) logic even in synthetic mode, for parity with live-FHIR cases)
  • A trajectory: Observation → Diagnosis → Intervention/Plan → Outcome, plus comorbidities that modulate or, where dosing-limiting, constrain the plan (built by deriveCheckpoints(c, cat)). Each comorbidity is itself a small node — its own diagnosis day, subtype/stage, and an independent, possibly-null escalation event (buildComorbidityNodes()) — not just a label on the primary case.
  • Encounter metadata (LOS, disposition, readmission flags), medications, symptoms, and free-text-flavored condition labels (conditionText(), matchCategory())

The "Use fixed seed (reproducible)" button pins seedRng() to a constant so the same 500-patient cohort — and therefore identical output across all 40 analytics — regenerates on demand, which is what makes the dashboard usable as a stable demo/teaching artifact rather than a fresh-random one every load.

FHIR integration

Fetch layer fhirFetch(baseUrl, path, headers) wraps fetch() with explicit handling for the fact that fetch() only rejects on network-level failure (CORS block, DNS, offline) — HTTP error statuses are checked separately so the UI can surface a real reason (auth, CORS, 4xx/5xx) instead of a generic failure.
Cohort assembly fetchFhirCohort(baseUrl, headers, maxPatients) pages Patient search results, then per-patient pulls Condition/MedicationRequest/Encounter/Observation bundles; bundleEntries(bundle, type) normalizes FHIR Bundle.entry arrays into flat resource lists that feed the same deriveCheckpoints() trajectory logic used for synthetic cases.

A visible pipeline strip (initPipelineSteps() / pipeStepEnter() / pipeMarkDone()) shows each stage — connect, page patients, fetch resource bundles, derive trajectories, run analytics — as it happens, with pipeAwaitDownloadOrProceed() gating on real network round-trips for the live-FHIR modes.

Analytics pipeline (40 passes)

Every pass is a pure function of the form analyticXxx(cases, ...) — it takes the in-memory cases[] array (plus, for a few, the RNG seed) and returns computed structures (aggregates, tables, distributions), with no shared mutable state between passes. renderAll(cases, valRows) calls all of them in sequence and hands each result to section() (builds the collapsible card shell), tbl() (renders a data table), and bars() (renders proportion/bar visualizations).

Custom query builder

renderQueryBuilder() lets a user compose ad-hoc filter rows (field, operator, value) against a fixed field list QB_FIELDS; qbBuildRow()/qbReadRow() read the row state, qbFieldByKey() resolves field metadata, and results run against the live cases[] array client-side — no query language, no server round-trip. queryBlock() renders the equivalent pseudo-code/ECL-flavored query text alongside the result, for transparency about what filter actually ran. Because QB_FIELDS spans every node type on the page (diagnosis, comorbidity, presenting symptom, demographic, SDOH flag, care-gap, utilization — the same presentation field the trajectory map's Presentation checkpoint and the symptom-proximity/ambiguity passes read from, now queryable directly, matched against c.symptoms via ALL_SYMPTOMS), any single field or any AND-stacked combination is reachable here, not just the ~30 combinations wired into the fixed passes above — this one panel is the general case the rest of the page's sections are specific instances of. The natural-language box ahead of it has two paths: with no BYOK key, qbParseNL() matches the phrase against a fixed keyword dictionary built from the same QB_FIELDS/CATEGORIES/COMORBIDITIES/ALL_SYMPTOMS (deterministic, no model call); with a BYOK key set, qbDraftNLQuery() instead sends the phrase and the same qbFieldCatalogForModel() catalog used by the closed-loop draft to the model and asks for STRICT JSON field/op/value triples — every named field and value is re-validated against the live catalog before any row is filled in, an unknown field or out-of-catalog value throws rather than being coerced, and a failed model call falls back to the offline lookup automatically. The same "Draft ECL from this ▸" button sits under the hypothesis field too, so a written hypothesis and a typed natural-language query both resolve through the identical draftFromText() path. Either path produces the same preset rows, the same generated ECL/FHIR text, and runs through the identical live filter — the model never computes a match count or a rate itself.

Visualizations

All charts and diagrams are hand-built SVG, not a charting library — renderTrajectoryMap() / renderTrajectoryInteractive() draw the six-checkpoint trajectory map with hub nodes sized by convergence; renderNetwork() draws the hub co-occurrence network with force-free, deterministic layout (connectedEdges() + draw()); renderPatientGraphSVG(c) draws the single-patient Observation→Diagnosis→Plan→Outcome graph shown in the case modal; renderForwardExplorer() and renderPivotExplorer() render interactive, re-computable mini-explorers inline in their sections.

Index case comparison

A single global INDEX_CASE (plain JS variable, not per-section state) lets one patient be pinned and compared against a benchmark group — its own category, or the whole loaded cohort, switchable on the fly via INDEX_CASE_SCOPE — across every analytic lens already on the page at once, from the #indexcase section near the top. Every comparison row shows an explicit "Compared against" cohort label (with its n) alongside the benchmark figure, so which group a given number was computed against is never implicit. Selection is always explicit: the trajectory map's own patient picker is now the primary chooser, kept in two-way sync with the index case, plus a direct picker in the comparison section itself.

UI shell & interaction

  • Every analytic lives in a collapsible section.block built by section(id, eyebrow, title, desc, quality); #collapseAllBtn toggles all sections at once. section() overrides the returned element's own appendChild so call sites can append straight into the collapsible body without reaching for a separate content reference.
  • The case explorer (renderExplorer()) and case modal (openCase(), backed by #caseModal) let you drill from any aggregate view into one synthetic (or live-fetched) patient's full trajectory, and from there pin it as the index case.
  • renderCatalog() renders the full 40-analytic catalog table (#catalog) as a reference index, independent of whether each analytic has been run yet.
  • Navigation is a static sidebar of in-page anchors (nav.side-groups) — no router, no history API; the whole app is one scrollable document.

Live hypothesis generation (BYOK)

One generalized pass, wired into all 26 sections renderLiveHypothesisPanel(analyticLabel, rawData) renders the button/output for one section, plus the "Test next hypothesis" closed-loop step described below it; runLiveHypothesisPass(analyticLabel, rawData, outEl, btnEl) does the actual OpenRouter chat-completions call for the hypothesis text itself. Neither is specific to any one analytic — every call site (all 40 numbered analytics plus trajectory, closed-loop, forward-pass, and cohort overview) just passes its own already-computed results array/object and a short label string. trimForModel() caps array payloads at 12 rows before sending; only that analytic's aggregate table goes out, never case-level data.
Key/model persistence The BYOK object ({key, model}) lives only in memory by default and is cleared on reload. Checking "remember" in initByokPanel() persists key + model slug through the artifact platform's window.storage API (personal, non-shared) rather than localStorage/sessionStorage — those don't reliably survive a reload inside this rendering sandbox, since each load can land in a fresh/isolated origin. hasStorage feature-detects window.storage and falls back to session-only mode with an explicit status message if it's unavailable.
Request shape & token budget A single POST to https://openrouter.ai/api/v1/chat/completions with a system prompt that forbids the model from computing or restating any number not already in the payload, and instructs it to pick 1–3 items worth attention, name a mechanism to check (as a question), and draft one next query — under 150 words, plain text, no markdown. max_tokens is currently 6000, deliberately generous because some OpenRouter models spend part of that budget on hidden reasoning before the visible reply, which can truncate a short answer if the budget is too tight.
Truncation & error handling The response's finish_reason is checked after every call: "length" renders the model's partial text plus a visible inline note telling the reviewer the reply was cut off and to retry or raise the budget, instead of silently showing a sentence that stops mid-word. Network/auth/quota failures render inline as .lh-error next to the button that triggered them, scoped to that one section — a failure on one analytic's panel doesn't affect any other.

Test next hypothesis (closed-loop query, BYOK)

The same closed-loop shape as project phase 04 (orchestrating clinical intelligence), compressed into one page: the model drafts the next coded query, code runs it, a human signs off twice.

Fixed catalog, not free-form code runHypothesisQueryDraft() sends the model only qbFieldCatalogForModel() and qbOutcomeCatalogForModel() — the same QB_FIELDS/QB_OUTCOMES the manual query builder above uses — never case-level data, and never an invitation to write its own filter code. The model must reply with strict JSON naming a field key, an operator, and a value; every named field, operator, and value is checked against the real catalog in runHypothesisQueryDraft() before anything is shown, so an unknown or malformed field fails loudly instead of silently degrading.
Two human checkpoints, same as phase 04 renderHypothesisDraftCheckpoint() shows the drafted, still-unexecuted query in plain language and asks the reviewer to approve or discard it before it touches the cohort at all (checkpoint 1). Only on approval does runApprovedHypothesisTest() build a real predicate from the same expr() functions renderQueryBuilder() uses and filter the live CASES array — no number here ever comes from the model. The result then waits on a second checkpoint, Mark as confirmed lead / Not supported — reject, before it's logged as anything more than a screening signal.
Wiring renderLiveHypothesisPanel() adds the "Test next hypothesis" button and its output slot under every existing "Generate next hypothesis" button, disabled until a hypothesis has actually been generated in that section (and re-disabled if the BYOK key is cleared). It reuses the generated hypothesis text as the model's input for the draft step — no separate prompt or button placement per analytic, same one-function-many-call-sites pattern as the rest of the live-hypothesis layer.
What this still isn't There's no second dataset in this app to replicate against, so this compresses phase 04's forward-pass-on-Dataset-B step into "re-run the same query after regenerating the cohort" — a weaker within-app stand-in for genuine independent replication, called out explicitly in the confirmed-lead message rather than implied.

LLM-assisted exploration loop (Build-your-own-query, BYOK)

This is where "any node, any combination" turns into "any planned or exploratory run of them": a multi-round version of the same closed-loop shape, scoped to the query builder instead of a single analytic. renderQueryExplorationLoop() runs a sequence of rounds, each one either a genuinely random combination sampled in code (qbRandomDraft() — true Math.random()-driven sampling, not the model claiming randomness) or a model-drafted round (qbDraftLoopQuery()) that reads a condensed history of prior rounds' already-computed results and chooses to go "deeper" on the strongest lead or "wider" into an untried field/value combination. Every round is evaluated by the same qbEvaluateConditions() function the manual query builder uses — filter, then rate/average per group, then lift — and every round's query is also rendered through each field's ecl()/fhir() mapping, the same illustrative SNOMED CT / FHIR shape used everywhere else in the suite, so a builder-oriented reviewer can see what this would look like against a real terminology and FHIR search, not just a JS predicate. Rounds that cross a fixed screening threshold (n\u22658, lift \u22651.3\u00d7 or \u22640.77\u00d7) are collected into a "candidate leads" list at the end, each gated by the same confirm/reject reviewer checkpoint as the single-analytic closed loop — nothing is auto-confirmed just because a threshold was crossed.

Scaling this to a product: direct FHIR connect + high-speed AI analytics

This build is intentionally a single static file with no backend, to keep it a zero-friction proof-of-concept. Turning the same pattern into a deployable product mainly means moving three things off the client and keeping the deterministic-compute/LLM-interpret/human-gate shape intact:

Direct, persistent FHIR connection Replace the on-demand, client-side fetchFhirCohort() calls with a server-side connector holding a standing SMART on FHIR / bulk-data ($export) session against the target EHR — OAuth2 client-credentials or backend-services auth instead of a pasted bearer token, and a proper token-refresh cycle. Bulk $export lets a production system pull the full Patient/Condition/MedicationRequest/Encounter set as NDJSON in one job instead of the current sequential per-resource, per-patient fetch loop.
A real cohort store, not an in-memory array Land the fetched resources in a columnar or analytics-oriented store (e.g. a warehouse table or an OMOP-shaped schema) behind the same case-shape mapping this app already does client-side, so every one of the 40 analytic functions can run as a query against indexed data instead of a full array scan in the browser on every reload.
High-speed AI analytics, same guardrails "AI for speed" here means the LLM accelerates which questions get asked and how fast a hypothesis becomes a coded query — not that it computes results faster by approximating them. Concretely: batch/cached hypothesis generation across the whole catalog instead of one BYOK call per section on demand, a background worker that pre-drafts and pre-validates candidate queries against the fixed field/outcome catalog between review sessions, and a vector index over prior findings so a new pattern can be checked against everything already screened before a human sees it — all still landing on the same two-checkpoint gate (draft approved before it runs, result approved before it counts) rather than skipping straight to a "confirmed" label.
What has to stay true Whatever the deployment shape, the core constraint that makes this trustworthy can't move: the model never becomes the source of a clinical number. A production version can add caching, indexing, streaming, and multi-tenant auth around that constraint — it should never add a path where an LLM-generated figure reaches a dashboard without having been recomputed by deterministic code against real data first.

Known limitations

  • No cohort/analytics persistence layer — the generated case data resets on reload; there is no backend database. The only thing persisted is an optional, opt-in BYOK key/model (via the artifact's storage, not localStorage/sessionStorage), and only if "remember" is checked.
  • No automated tests; correctness of the 40 analytic passes relies on deterministic-seed manual review.
  • Large custom-FHIR pulls (hundreds of patients × multiple resource types) are fully sequential client-side fetches with no caching layer, so response time scales with server latency and patient count.
  • Not validated against real clinical outcomes and not intended as clinical decision support — see About.
  • Comorbidity nodes (stage, own diagnosis/escalation day) are drawn from a plausible random distribution per comorbidity, the same way every other synthetic field is — they are not a real disease-staging or progression model, and the "leads X% of the time" sequence read in analytic 2 should be treated with the same case-control-tier caution as the rest of the suite, not as a validated clinical order of events.
  • The live hypothesis panel attached to every analytic below is opt-in and requires a person-supplied OpenRouter key; it sends only that analytic's already-computed results table (never case-level data) to whatever model is selected, and the model is instructed never to compute a number — but that instruction is a prompt, not a guarantee, so its output should be read with the same "flag for a human, not a finding" caution as every other LLM note in this suite.
  • Reasoning-capable models routed through OpenRouter can still exhaust the 6000-token budget on hidden reasoning before writing a visible reply; the app surfaces this explicitly via finish_reason==="length" rather than silently truncating, but a person may still need to retry or pick a different model on some providers/models.
  • "Test next hypothesis" only ever tests one query against the one live in-memory cohort — regenerating the cohort and re-approving the same draft is the closest this app gets to replication, not an independent second dataset the way phase 04's real forward-pass step is; a "confirmed lead" here means "held up when re-run," not "replicated externally."
  • The model's drafted query is constrained to the fixed QB_FIELDS/QB_OUTCOMES catalog and validated before use, but a model can still draft a clinically implausible or low-value combination (e.g. two conditions that are already known to be identical) — the query-verification checkpoint exists specifically so a reviewer catches that before it runs, not after.
  • The exploration loop's "random" rounds are true code-side Math.random() sampling and are not reproducible the way the seeded synthetic cohort is — running the loop twice on the same fixed-seed cohort will still try different random combinations each time, by design, since the point of that round type is breadth, not repeatability.
EVIDENCE-PYRAMID MAPPING

▾Where the 40 analytics sit on the evidence-based-medicine pyramid

Mapped against the classic EBM hierarchy, almost all 40 passes cluster in the lower-middle of the pyramid: observational, hypothesis-generating, cohort- and case-control-level work. Nothing here reaches randomized-trial or meta-analysis level, because nothing is randomized and nothing synthesizes external studies — and three passes don't try to climb the pyramid at all, they audit local practice against evidence that already sits at its top.

Short version: most of the suite lands at the cohort-study tier (associations across the whole population, no control arm) or the case-control tier (retrospective pattern-mining, single-case trajectories). Analytics 20–22 (guideline adherence, care gaps, symptom burden) are a different kind of thing — they apply evidence that already exists rather than generating new evidence.

Pyramid, bottom to top

Teal bands = tiers the 40 analytics actually reach. Guideline/care-gap/symptom-burden passes (20–22) sit outside this stack — see the table below.

Why this matters for how you read the output

  • No causal claims. A lift ratio or co-occurrence rate at this tier is an association, not a mechanism — it's a lead for a real study, not a finding to act on directly.
  • One cohort, no external replication. The drift check (analytic 12) tests stability across two pulls of the same generator, not replication in an independent population.
  • Synthetic data compounds the gap. This mapping describes where the method sits on the pyramid; it says nothing about whether a synthetic cohort's numbers would hold on real patients.
  • Guideline audits are the exception. Analytics 20–22 don't inherit these limits the same way, because they check conformance to evidence that already cleared the top of the pyramid elsewhere.
  • The optional live hypothesis layer doesn't move anything on this pyramid. When a BYOK key is set, the LLM only restates and interprets numbers a deterministic pass already computed — it never sees case-level data and never computes a number of its own — so it's a narration layer on top of whichever tier the underlying analytic already sits at, not a new rung.
  • Neither does the closed-loop "test next hypothesis" step. It lets the model draft the next coded query, but the query itself only ever produces another case-control or cohort-tier comparison on the same synthetic or single-server cohort — it doesn't add a control arm, randomization, or an independent replication dataset, so a "confirmed lead" from it still sits at the same tier the underlying analytic did, gated by two human checkpoints rather than promoted by them.
  • Build your own sits at the same tier too — by construction, not by accident. Every ad-hoc query out of the custom builder — hand-built, deterministic-lookup NL, or model-drafted NL — runs through the identical expr()/filter mechanism as the 40 fixed passes, so a one-off query lands at case-control tier (a with/without comparison on one field) and a full exploration-loop run lands at cohort or case-control tier depending on the outcome type, exactly like its fixed-pass equivalent. Letting a person or a model pick the field doesn't change what kind of evidence running that field produces.
